Set up, run, and test Continuum Core

The unified process-to-agent model, its guardrail enforcement, and the governance and dashboard apps — how to stand them up and prove they work. Run every command from the continuum-core/ directory.

§ Prerequisites & one-time setup

Python 3.10+ (developed on 3.14). The core engine is standard-library only; nothing in this manual needs the network. Create a virtual environment and install the three dependencies used by the server, harness, and apps.

bash · one-time 
cd continuum-core
python3 -m venv .venv
. .venv/bin/activate                 # Windows: .venv\Scripts\activate
pip install -r mcp_server/requirements.txt   # mcp, tiktoken, jsonschema

Prefer not to activate the venv?

Everything below assumes the venv is active. If you'd rather not activate it, replace python3 with .venv/bin/python in every command.

About exit codes

All suites exit 0 on success. traceability.py exits 1 only on a hard broken reference — never for the expected 3 warnings, which represent deliberately planted data-quality defects.

§ Using it, phase by phase

01

Model, MCP tools & token budgets

The locked 8-entity data model, a hand-built 8-domain graph, and the three agent-facing MCP tools — with §08 token budgets validated by a real tokenizer.

bash 
python3 mcp_server/continuum_core.py        # the four agent payloads
python3 mcp_server/token_budget.py --validate  # schemas + §08 budgets
python3 mcp_server/traceability.py         # §01/§12 data-quality lint
python3 mcp_server/scenario.py             # agent tool loop, tokens on the wire
LOOK
What to look for: scenario.py shows one agent going through allow / escalate / deny / out-of-scope, every response under budget. traceability.py flags exactly 3 planted defects (2 orphan KPIs + 1 process with no strategic parent) — proof the linter works.

Register the MCP server with an agent

Use the venv Python (so the mcp package is found) and absolute paths. Running server.py directly just blocks waiting on a client over stdio — that's expected.

bash 
claude mcp add continuum -- \
  /ABS/PATH/TO/continuum-core/.venv/bin/python \
  /ABS/PATH/TO/continuum-core/mcp_server/server.py
02

Govern the guardrails — edit without a deploy

A web app where a process owner edits a Guardrail Policy; the edit is validated, versioned, and recorded (ISO 9001 §7.5), and is instantly live for agents.

bash 
python3 governance/test_store.py   # prove the write path (14 asserts)
python3 governance/app.py          # open http://localhost:8787
  • Click a process (e.g. CO.3.2.7).
  • Change Escalate if from risk_score > 0.7 to risk_score > 0.95.
  • Fill a Reason for change (required) and click Save new version → the badge goes v3 → v4.
  • Try an invalid condition like risk_score >>> 0.5 → it's refused, version unchanged. Bad policy can't reach agents.
PROVE
One source of truth — with the edit saved, an agent reading over the MCP core sees it immediately:
bash · expect: 4 risk_score > 0.95 
python3 -c "import sys; sys.path.insert(0,'mcp_server'); import continuum_core as c; g=c.Graph(); gr=g.get('GuardrailPolicy','gr.CO.3.2.7'); print(gr['version'], gr['escalate_if'])"
Reset with rm data/edits.log.jsonl (back to v3).
03

Enforce the guardrail & check the model against reality

The Enforcement Point (a real gate — the tool runs only on allow) wired to a pilot agent, plus the Conformance Check that compares the model to reality (§06).

bash 
python3 enforcement/pilot_agent.py    # every action routed through the EP
python3 enforcement/test_enforce.py   # 13 asserts: tool runs ONLY on allow
python3 signal/conformance.py         # §06 drift report (human-review-only)
python3 signal/test_conformance.py    # 8 asserts: never mutates the model
LOOK
What to look for: the pilot runs the tool only on the allow case; escalate goes to a human queue; deny / out-of-scope / rate-limit block. conformance.py reports 5 drift types — including an agent that ran under a stale guardrail — each marked needs human review.
04

Enforce everywhere & read the standing report

Enforcement across all agent-bound tasks, and the §05 strategy-to-execution dashboard.

bash 
python3 enforcement/sweep.py --keep   # all 8 bindings + keep the activity log
python3 dashboard/app.py             # open http://localhost:8788
python3 dashboard/test_rollup.py     # 13 asserts
python3 audit/verify.py             # verify the audit hash chain (exit 1 on tampering)
LOOK
On http://localhost:8788: metric tiles (guardrail coverage 12% — 1/8 reviewed, honest; traceability 88%; agent activity), each objective with its KPI status and the agent-bound tasks beneath it, the coverage panel, and bottom-up traces. Two metrics read needs data on purpose — see Known limits.

The dashboard is empty until you populate it

Run python3 enforcement/sweep.py --keep (or pilot_agent.py) first — the dashboard reads the agent action log those write.

§ Data & reset

The model lives in data/seed.json (committed). Everything the running system writes is runtime state, git-ignored, and safe to delete to reset.

§ Known limits

Each is gated on something this environment can't provide, and each is declared with a real interface and a stand-in — never silently faked.

  • Live enterprise connectors (Notion, Teams, Slack, Outlook, Gmail) need OAuth. They raise a clear error if called; FileConnector + the signal/*.sample.jsonl fixtures stand in so the Conformance Check runs for real. Enable order lives in SENSITIVITY_ORDER.
  • The pilot agent is a deterministic Python loop, not a live LLM — it exercises the Enforcement Point exactly as a real MCP/Claude agent would, without needing model access.
  • Two §12 metrics show needs data: escalation precision (needs humans to disposition escalations) and drift-to-update latency (needs finding + resolution timestamps). Supply dispositions to Rollup.metrics(...) and escalation precision computes.
  • Guardrail coverage is 12% (1/8) by design: only the KYC guardrail was reviewed and signed off; the rest run under defaults. That is the coverage metric working, not a bug.
